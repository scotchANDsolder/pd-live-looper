# pd-live-looper

A Pure Data patch for live music performance: load up to 10 WAV files simultaneously, loop each continuously, and control every loop's start point, end point, playback speed, effects, and output routing in real time.

## Status

**Phase 2 (current):** 10-track loop player, generated from a single-track template

- `01_engine_10tracks.pd` + `02_gui_10tracks.pd` are the files to actually use — 10 independent copies of the track engine and rack GUI below, each with its own isolated audio (no cross-talk between tracks) and its own `loopergui_*_tN` send/receive namespace so each rack only controls its own track
- `01_single_track_loop.pd` + `02_gui_control_panel.pd` are the single-track template these are generated from — still fully functional standalone (open both together for a 1-track setup), and the source of truth if you want to change something for all 10 tracks
- `scripts/generate_10tracks.py` regenerates the 10-track files from the templates — run it after editing either template file. It renumbers every object index and `#X connect` line, so hand-editing the generated 10-track files directly is not recommended; edit the single-track templates and regenerate instead

**Phase 1 feature set** (present in every one of the 10 tracks):
- Load a WAV via file picker
- Loop start / end set as a **percent (0-100)** of the sample's length, not raw sample counts
- Playback speed as a multiplier (1 = normal); pitch shifts with speed, tape-style
- Dual audio interface output: independent play/stop toggles for interface 1 (`dac~ 1 2`) and interface 2 (`dac~ 3 4`), so you can route to either one or both simultaneously. The loop position only freezes when *both* are off; while either is on, the underlying `phasor~` keeps running (position preserved), and each interface has its own mute stage so it can be silenced without affecting the other
- Waveform display
- Echo effect: on/off toggle, delay time (1-2000 ms), feedback (0-0.95), wet mix (0-1)
- Reverb effect: on/off toggle, decay (0-0.9), wet mix (0-1) — Schroeder-style, 4 parallel comb filters into 2 series allpass filters
- Master volume slider (0-1.5) on the output stage
- Separate GUI control panel, styled like a synth rack, driving every control via Pd send/receive — see below
- Loaded filename shown live in the rack (top-left of each TRANSPORT module), so you can tell which WAV a given rack is controlling without checking the engine file

**Planned next:**
- Reverse per track
- MIDI controller mapping for all parameters

## Requirements

[Pure Data (Pd) vanilla](https://puredata.info/) 0.52+, or [plugdata](https://plugdata.org/) (same patch works unmodified, nicer UI).

## Usage

Open **both** `01_engine_10tracks.pd` (the DSP/engine, all 10 tracks) and `02_gui_10tracks.pd` (10 stacked rack panels) in the same Pd instance — File > Open both, or drag both onto Pd. They're linked purely by matching `send`/`receive` names, not a subpatch/abstraction relationship, so either window can be closed and reopened independently and they'll reconnect automatically as long as both are open. (For a single track instead, use `01_single_track_loop.pd` + `02_gui_control_panel.pd` the same way.)

In `02_gui_10tracks.pd`, scroll down through the 10 "TRACK N" racks. In each: click **load** to pick a `.wav` file for that track, use **play1**/**play2** to start/stop that track's output to interface 1 and interface 2 independently (on for just one, both, or neither — every track shares the same two physical interfaces, `dac~ 1 2` and `dac~ 3 4`, and whatever's routed to a given interface from multiple tracks just mixes together), and adjust that track's **start%/end%/speed/volume** faders plus its own **ECHO** and **REVERB** module faders. Every track's controls are fully independent of every other track's.

`01_engine_10tracks.pd` has its own original number boxes and toggles for every track scattered near each track's DSP chain — those are the actual "wiring" the GUI drives (via small `r loopergui_*_tN` receive objects) and still work if you interact with them directly, but they're not meant for regular performance use now that the rack panel exists; that file is really just meant to stay open in the background providing the audio engine.

## Notes

The patch is hand-written in Pd's text file format rather than built through the Pd GUI editor. A few objects exist purely to work around Pd quirks worth knowing if you're editing this:
- `route symbol` + `list prepend`/`list append`/`list trim` before `soundfiler`, so file paths containing spaces don't get split into multiple message atoms
- `pack`/`unpack` refresh chains around the loop-length and frequency calculations, since Pd's `expr` object only treats its leftmost inlet as "hot" (triggers recompute) — without this, changing `end` or `speed` alone would silently update a stored value without ever refreshing playback
- The echo effect is wired as an always-on-dry send/return rather than a wet/dry crossfade: the dry signal passes through unchanged, and the delayed signal is added on top (gated by the on/off toggle) before the play/stop mute stage. This sidesteps the same `expr` hot-inlet refresh problem entirely — no recompute chain needed for the mix
- `+~`/`-~` and friends: giving them a creation argument (e.g. `+~ 0`) locks the right inlet to float-only — it silently stops accepting a signal. The echo feedback sum and the final wet/dry mixer both needed a live *signal* on their right inlet, so those two are declared as bare `+~` (no argument); Pd will silently drop a signal connection into a non-signal inlet with a console warning ("audio signal outlet connected to nonsignal inlet") and never actually mix the audio, which is exactly what a `+~ 0` there would do
- The source freeze-on-stop uses the same pack/trigger/unpack refresh idiom as the loop-length/frequency chain, gating the frequency signal fed to `phasor~` (0 = frozen in place) rather than just muting the output, so stop/resume preserves loop position and live parameter edits still take effect immediately whether playing or paused
- Reverb is a classic Schroeder structure: 4 parallel comb filters (`delwrite~`/`delread~` with a `lop~` damping filter in the feedback path, all sharing one decay control) summed together, then through 2 series allpass filters (fixed coefficient 0.5) for diffusion. Like echo, it's an always-on-dry send/return rather than a crossfade
- The GUI is a genuinely separate `.pd` file, not a subpatch/abstraction embedded in the main patch — Pd's `send`/`receive` names are global across every open patch in the same instance, so `02_gui_control_panel.pd`'s widgets each `send` to a `loopergui_*` name that a small `r` (receive) object in `01_single_track_loop.pd` picks up and forwards into the real DSP-connected widget's inlet. This is one-directional (panel → engine only): the panel's sliders are given a `default_value` that visually approximates the engine's actual startup defaults, but they aren't live-synced back, so if the engine's own widgets are changed directly the panel won't reflect it
- The rack look in `02_gui_control_panel.pd` uses `cnv` (canvas/panel) objects as solid-color background rectangles for the dark base plate and each module's faceplate, since Pd's file format has no separate "patch background color" property that's safe to hand-write across versions — layering `cnv` objects (dark background, lighter module panels, then the actual controls on top, in that file order so they draw over the panels) is the standard vanilla-compatible way to fake a custom-colored UI. IEMGUI label fields (the inline label on `cnv`/`tgl`/`vsl` etc.) are whitespace-tokenized like everything else in the `.pd` format, so multi-word labels use `wetmix`/`delay_ms` instead of spaces rather than risk silently misaligned fields
- Dual-interface output shares one volume stage but has two independent mute gates, one per interface, each gated by its own toggle — the signal order is mixer → volume → per-interface mute → that interface's `dac~`. Whether the *source* itself is frozen (see freeze-on-stop above) is driven by `expr max($f1, $f2)` over both interface toggles (via the same pack/trigger/unpack refresh idiom, so a change to either toggle alone still recomputes correctly) — the loop only pauses when both interfaces are off, so switching between "just interface 1" and "just interface 2" doesn't audibly restart the loop. Note: `expr`'s comma inside `max($f1, $f2)` has to be escaped as `\,` in the `.pd` file for the same reason the semicolon fix earlier in this doc was needed — unescaped, it's a statement separator at the file-format level, not just inside message boxes, and silently corrupts the object after it
- The 10-track files are generated by `scripts/generate_10tracks.py` rather than built as Pd abstractions instantiated 10 times. Pd abstractions with `$1`-style creation arguments are extremely standard, but in this environment's headless `-nogui` batch-mode testing, even the most minimal textbook abstraction pattern (`+ $1` instantiated as `myabs 5`) failed with the same "`$1`: argument number out of range" error the very first semicolon bug in this doc produced — with no way to test real interactive Pd here (no virtual display available) to confirm whether that's a genuine environment limitation or something else, the safer choice was a code-generation approach fully verifiable with the same headless testing used throughout this project, rather than trusting a mechanism that failed a basic sanity check. This also sidesteps a real bug copy-pasting would otherwise introduce: `delwrite~`/`delread~` names are global in Pd (not lexically scoped like arrays), so 10 literal copies of e.g. `delwrite~ echoline` would all collide on the same buffer; the generator suffixes every delay-line name, the array name, and every `loopergui_*` send/receive symbol with `_tN` per track. If you ever want to try the abstraction route again (cleaner architecture, if it works) — test it in a real interactive Pd session first
- The live filename display uses `symbolatom` (the text-display counterpart to the numeric `floatatom` boxes used everywhere else in this patch, but one this project hadn't used before this feature). Two format gotchas worth knowing: (1) like `floatatom`, it's declared with its own dedicated `#X symbolatom ...` file-format tag rather than `#X obj ... symbolatom ...` — writing it the generic way fails silently with "couldn't create"; (2) it only accepts a properly-tagged `symbol <value>` message, not a bare word — a message box containing just `sounds/kick.wav` sends a message *named* `sounds/kick.wav` with no arguments (Pd treats the first word of a message box as the selector), which `symbolatom` rejects with "no method for ...". `openpanel`'s own output is already correctly `symbol`-tagged (this project's file-load chain already relied on that via `route symbol`), so the engine just taps it directly and sends it out over `loopergui_filename` — no extra wrapping needed. The generator script had to learn about `#X symbolatom` lines too, both for Y-offsetting per track and for object-index counting, and `process_gui()` needed a real rewrite to offset connect indices at all: before this feature, the GUI file had zero internal `#X connect` lines (every widget just used its own `send` field), so the generator never needed to touch connect indices for it — the receive→symbolatom wire is the first one, and copying it verbatim into all 10 racks without offsetting would have wired most of them to whatever objects happened to land on the literal same index from track 1
